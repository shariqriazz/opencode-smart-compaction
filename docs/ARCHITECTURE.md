# Architecture

The plugin registers OpenCode 2 session hooks for `compaction`, `context`, and `generate`. It supplies the checkpoint as the compaction hook's result, so OpenCode skips its own summary request. The request hooks bound oversized recent-context blocks on marked checkpoints without changing stored messages. A watcher adds the hybrid compaction threshold, tracks warm-cache usage and running shells, and the compaction hook lists background subagents that haven't reported back.

## Key files

- `src/index.ts`: the plugin definition (`{ id, setup }`), the compaction hook with its model attempts, and the event watcher's start.
- `src/session.ts`: reads the previous checkpoint and its verbatim recent context, user text, accumulated file activity, and a bounded transcript from the request messages.
- `src/checkpoint.ts`: builds the prompt, checks the summary's sections, and completes the summary.
- `src/cache.ts`: pure cache-reuse eligibility and the latest ended step per session.
- `src/model-limits.ts`: one cached model-limit lookup shared by cache reuse and the threshold watcher.
- `src/prompt.ts`: the checkpoint prompts, protected-fact extraction, and file-state formatting.
- `src/git-state.ts`: dirty files and a bounded diff with untracked-file previews.
- `src/events.ts`: the single event-stream loop.
- `src/shells.ts`: running shells per session.
- `src/subagents.ts`: background subagents that haven't reported back.
- `src/recent.ts`: finds and adapts the kept stored turns for summary coverage, and deterministically bounds recent context in requests.
- `src/threshold.ts`: the hybrid threshold options and the step watcher that requests compaction.

## How it works

1. OpenCode splits the session into an older part to summarize and a recent part it keeps verbatim (`compaction.keep.tokens`), then calls the `compaction` hook. OpenCode 2.0 passes only the older part as `event.messages`; OpenCode 2.1 passes the whole conversation and records the start of the kept part as `metadata.keepID`, rebuilding the kept text from it. Stored compactions carry that text as `recent` in 2.0 and `metadata.recent` in 2.1 (`storedRecent` reads both).
2. When a previous checkpoint exists, it is the first message, wrapped in `<conversation-checkpoint>`. `readSessionFacts` takes its summary out and returns the new conversation as a transcript. The previous checkpoint's `<recent-context>` is included unless the summary already marks it as covered; those turns no longer appear individually in the active context. The transcript includes user and assistant text, reasoning excerpts, tool calls with large arguments bounded, and tool results that keep their beginning and end within a per-tool budget (more for errors and the newest 14 messages; shell output loses terminal escape codes and repeated lines). It also collects user text and file activity: `read` for read files; `edit`, `write`, and the `*** Add/Update/Delete File` and `*** Move to` lines of `patch` for changed files, skipping calls whose result is an error. File activity from the recent context's tool-call lines and from the file lists appended to the previous checkpoint is added, so the lists accumulate across compactions; each list keeps only its most recently used paths (40 read, 60 changed), listed from least to most recently used so the order carries into the next compaction.
3. The plugin looks up the session's directory and model (`ctx.session.get`) and reads its git state. A failed or oversized tracked diff gets an omission notice without discarding the status inventory or lockfile/generated-asset list. It reads the session's active context (`ctx.session.context`: every stored message since the last compaction, including the turns OpenCode will keep verbatim) for background subagents: a `subagent` tool part whose `metadata.status` is `running` starts one, and a synthetic message with `metadata.source` `subagent` and the same `metadata.childID` ends it. A completed foreground report for the same child also clears it. Subagents listed in the previous checkpoint's `<running-subagents>` block are carried in first, since their launch may predate the context. A verified carried list is authoritative as of that checkpoint: only newer live structured records or rendered completion tags in newer synthetic messages can end those entries. When the previous block starts with the unverified note, rendered `<subagent sessionID="…" state="completed|error|cancelled">` reports in the request checkpoint, transcript, and stored completed checkpoints (summary and recent context) also clear carried IDs; newer live launches can resume the same child. If context can't be read, remaining carried children are explicitly marked unverified, not asserted to be still running.
4. `buildCheckpoint` assembles the stateless prompt: the directives, the transcript in `<conversation>`, the previous checkpoint in `<previous-summary>` with its appended state stripped (`semanticSummary`), the protected facts, and the initial or update instructions. It also builds a cached-path prompt from the same directives and six-section format, without repeating the transcript or checkpoint. That prompt tells the agent to stop working, call no tools, and summarize the entire session, including the newest turns. A previous checkpoint gets the same delta-merge retention rules; its automatically appended state must not be copied. Both paths share the computed file-state appendix, with separate coverage markers.
5. When the cache guards below pass, `ctx.session.generate` tries the cached prompt first. Otherwise, or after an incomplete/empty reply or retryable error, `ctx.generate.text` runs the stateless prompt on the compaction model (`event.model`: the session's model, or `agents.compaction.model` when set). The model reference carries the variant, so its reasoning settings apply. Stateless retries still use `summaryModels`: the compaction model with its variant, the same model without its variant, then the session's model without a variant, deduplicated. `isCompleteSummary` requires all six numbered section headings, line-anchored and in order outside code fences, with non-empty content after section 6, since the API reports no finish reason. `isFatalGenerationError` (cancellation, authentication, permission, quota) stops the attempts.
6. `completeSummary` first removes model-copied reserved appendix blocks, then restores dropped protected facts and appends our exact state. Removal covers complete paired and self-closing blocks whose opening tag starts a line at column 0, including single-line forms; inline mentions, indented code, and fenced code examples stay unchanged. A fence the model left open is closed, so the appended state never lands inside it. Section validation runs on the stripped text. Leftover blank-line runs outside fences collapse. Coverage is authoritative only when the extracted summary, after trimming trailing whitespace, ends with the exact marker block our appendix emits last. Fenced examples and mid-summary markers cannot authorize trimming or suppress recent turns from the next compaction transcript. Dirty files and lockfile/generated-asset changes are sorted and each capped at 60 paths with an explicit omission count. The blocks also include the session's running shells from `createShellTracker` and its running subagents with a note not to poll, relaunch, or duplicate them (or an unverified-status note after a failed context read). OpenCode stores `event.result.summary` as the checkpoint before the recent conversation.

### Cache-reusing generation

`cacheReuse` defaults to `true`; `false` keeps only stateless attempts. `cacheReusePlan` (`src/cache.ts`) is a pure guard that returns either an output cap or a skip reason. It requires all of these:

- Session context was read, and every stored assistant message has `time.completed`. `SessionHistory.preview`, which builds the `session.generate` history, drops everything from the first unfinished assistant onward, so such a history can't grant full coverage.
- The session's latest ended step used the compaction model (same provider, model ID, and variant), started less than 270 seconds ago, and reported cache reads or writes. The start time is used because the provider reads the cache when the request is sent; tool execution can end the step much later. A separate `agents.compaction.model` therefore always takes the stateless path. A newer cold step replaces an older warm one, and compaction end and session deletion clear the record.
- The step's assistant message is in the session context. Its tool results and every later message were added after the step's request was measured, so they are estimated (JSON characters divided by four) and added to the step's tokens (input, cache read and write, output, reasoning) and `ceil(cachedPrompt.length / 4)`.
- The model window (`limit.context || limit.input`) is known and, after that projected input and an 8,000-token margin, at least 4,096 tokens remain. A positive `limit.input` must also hold the projected input plus the margin. The output cap is the smallest of the room, 32,000, and a positive `limit.output`.

`ctx.session.generate` builds the request from the session's agent, model and variant, system prompt, tools, and stored history since the last compaction, appends the prompt as a user message, and doesn't change the session. When that prefix matches the last agent request, OpenCode's usual cache breakpoints and affinity headers let the provider read it from the cache.

These requests run the `generate` hook, not `context`. The plugin registers `generate` whenever trimming or cache reuse is on. It applies the same deterministic trimming as the `context` hook. For the plugin's own summary request, recognized by its prompt as the last user message, it caps `options.maxTokens` without raising a smaller existing cap. If the session's model changed after the guard ran, it throws instead, so the cached attempt fails and the stateless attempts run. Session generation has no default output cap, and Anthropic's default of 32,000 plus a near-full window would be rejected. Other plugins that change agent requests in `context` must make the same change in `generate`, or the prefix won't match.

### Diagnostics

Successful results carry `metadata.smartCompaction`: `mode` (`cached` or `stateless`), `model` (`provider/id#variant`, empty after `#` for the default variant), `durationMs`, `summaryChars`, `promptChars`, and `attempts`, each with mode, model, milliseconds, and an outcome of `ok`, `incomplete`, `empty`, or an error message capped at 200 characters. `cacheSkipped` names the guard that skipped the cached path. In OpenCode 2.1 it sits beside OpenCode's own `keepID`. The server log gets one info line per checkpoint, or one warning listing every attempt when the plugin falls back; both include `cache-reuse-skipped=<reason>` when it applies. Diagnostics never contain transcript or summary text.

### Bounding kept context

With `maxRecentTokens > 0` (default 40,000), the compaction hook uses request message IDs to find the last older message in `ctx.session.context`. When a previous checkpoint has no request ID, its summary can instead be matched exactly against a stored completed compaction. Stored turns after the boundary are adapted to the transcript message shape and passed through `readSessionFacts` with the older messages, so their user facts, file activity, errors, and resume state are included in the checkpoint. Synthetic, skill, and system context is labeled separately from user-authored intent; shell results use the same bounded serializer as other tool results. A `recent-context-summarized` appendix marks that coverage. The stateless path adds no marker when context cannot be read, the boundary cannot be matched, or transcript-bearing content such as user attachments cannot be adapted. The cached path sees every stored message, so a successful cached summary gets the marker whenever `maxRecentTokens > 0`, independent of adaptation.

The `context` and `generate` hooks shorten only a marked checkpoint's recent block. They estimate tokens as characters divided by four, keep the newest portion at a turn boundary when possible, and add an omission note. Copies preserve message and part prototypes; stored messages remain unchanged. The cut depends only on the text and budget, so repeated requests have the same prefix. On the next compaction, a marked checkpoint's recent text is still read for protected user facts and file activity but isn't added to the semantic transcript again. Unmarked checkpoints keep the old behavior. `maxRecentTokens: 0` disables extra kept-turn adaptation, coverage markers, and trimming, but does not disable cache reuse.

Manual compaction places an empty running-compaction record in the stored context before the hook runs. That placeholder and idle records have no conversation to cover. Earlier failed compactions contribute a labeled, bounded error; completed checkpoints inside the kept tail remain unsupported rather than silently losing their summaries.

### Events

`subscribe` (`src/events.ts`) runs one loop over `ctx.event.subscribe`; the setup's returned cleanup aborts it.

- `createShellTracker` (`src/shells.ts`) keeps running shells from `shell.created`, keyed by shell ID and tagged with `metadata.sessionID`, which OpenCode's shell tool sets, and drops them on `shell.exited` or `shell.deleted`.
- `createCacheTracker` (`src/cache.ts`) records each step's model and start time from `session.step.started` and its token usage from `session.step.ended`.
- `createThresholdWatcher` (`src/threshold.ts`) implements the threshold below.
- Model/provider updates invalidate the shared model-limit lookup, even when the threshold is off.

### Threshold

OpenCode's own automatic compaction runs only at the model window minus `compaction.buffer`. The watcher remembers each session's model from `session.step.started`, and on `session.step.ended` adds up the step's input, cache, output, and reasoning tokens, the same measure OpenCode uses. When that reaches the threshold (hybrid by default: the lower of 95% of `limit.input || limit.context` and 600,000), it calls `ctx.session.compact`. OpenCode delivers the request at the next step boundary, so an agent loop that was mid-task continues after the checkpoint. One request is outstanding per session; a session whose compaction failed is left to OpenCode's own trigger until a compaction succeeds. A per-session generation advances on each compaction start, end, or failure, so a model-window lookup cannot trigger compaction from stale pre-compaction usage.

## Decisions and trade-offs

- **The plugin writes the summary.** OpenCode appends its own summary template after hooks run and rejects replies that don't use its headings. Supplying `event.result` is the only way to use the six-section format without fighting that template.
- **Independent of Pi.** `src/prompt.ts` and `src/git-state.ts` began as adaptations of the Pi extension's `prompt.ts` and `engine.ts`, but the plugin is maintained on its own and its checkpoint format follows OpenCode's needs.
- **Size budget.** OpenCode keeps recent turns verbatim beside the checkpoint, so the prompt asks for at most about 1,500 words, keeps an updated summary near the previous one's length, and tells the model not to repeat the appended file lists and diff.
- **Fail open.** When every attempt fails or is incomplete, `event.result` stays unset, so OpenCode compacts with its own prompt and its own size handling. Pi cancels compaction instead; in OpenCode a cancelled automatic compaction would leave the session at its limit.
- **No runtime dependencies.** The plugin imports only OpenCode types. `Plugin.define` is an identity function, so the default export is a plain object checked with `satisfies Plugin.Plugin`.
- **No size retry.** OpenCode shrinks its own compaction request when a provider rejects it as too long. The plugin does not shrink a rejected request: a cached failure moves to bounded stateless attempts, and if those fail OpenCode's own compaction takes over.
- **Cached first, bounded fallback.** A warm, matching `ctx.session.generate` request lets the model summarize the full conversation, including complete tool output, with most input billed at the cache-read rate (in live tests, 93-94% of input tokens came from the cache). The bounded transcript can be fewer billed tokens on a small session, since it keeps only a bounded excerpt of each tool result (`toolResultBudget`), but it loses detail, and on large sessions it is billed at the full input rate. A cold or mismatched prefix makes the cached request cost more than the transcript, so the guards skip known poor cases. The stateless `ctx.generate.text` fallback doesn't run session request hooks (`model.request`, `http.request`) or agent overlays, returns no usage, and has no cancellation or reasoning override.
- **Serialization lives in `session.ts`.** The transcript budgets follow the Pi serializer in substance but are written for OpenCode's message parts and tool names (`shell`, `patch`, `glob`, `oldString`/`newString`, `patchText`), so they live apart from `prompt.ts`.
- **Threshold after the step.** The threshold uses the size a step reported, so it compacts before the next step rather than cancelling the current one. OpenCode's own buffer threshold, which estimates before each request, stays as the backstop; a buffer larger than the plugin's margin makes OpenCode compact first.

## Gotchas

- **Entry point.** OpenCode loads an npm plugin from the package's `./server` or `.` export, and a local directory plugin only from an `index` or `server` file at its root. This package uses the `.` export, so test it from npm or from a file under `.opencode/plugins/` that re-exports `src/index.ts`.
- **OpenCode's serialized formats.** `parseCheckpoint` depends on the checkpoint wrapper in OpenCode's `session/runner/to-llm-message.ts` (summary, then a `recent-context` block), and `recentToolCalls` and `recentUserTexts` depend on the `[User]:` and `[Assistant tool call]: name(json)` lines that `messageToText` in `session/recent-text.ts` (`session/compaction.ts` before OpenCode 2.1) writes. A change there silently drops recent turns or file activity.
- **Buffer coupling.** The plugin's percentage threshold only takes effect when OpenCode's own `compaction.buffer` leaves a smaller margin; with the default buffer (15% since OpenCode 2.1, 10% before), OpenCode compacts at 85% (or 90%) first.
- **Literal tags.** Prompt and appendix strings contain XML-style tags (`<previous-summary>`, `<touched-files>`, and others). Some editing tools hide those tags in their display; check the file bytes rather than the rendered view when editing them.
